# План: функции game.exe без реализации в ремейке

Цель — найти среди функций game.exe, для которых в `remake/src` нет .py файла, те, что нужны `make demo`,
разобрать их и перенести в Python. Остальные — отметить как ненужные или отложенные. Исходные данные —
реестр [`func_registry.json`](func_registry.json) и его сводка [`FUNC_REGISTRY.md`](FUNC_REGISTRY.md)
(`make registry`). Цифры ниже — на 2026-11-11.

## 1. С чего начинаем

Без ссылки из .py — 8750 функций (`missing`) и ещё 1287 (`indirect`), которые вызываются из реализованных
функций, но сами нигде не названы. Вместе 10037 функций. Подсистема каждой функции угадана
`tools/func_domains.py` (раздел «Покрытие по подсистемам» в FUNC_REGISTRY.md). По уровню они делятся так:

| Уровень | missing + indirect | Строк C | Что это | Решение |
|---|---:|---:|---|---|
| `backend` | 1839 | 84 тыс. | STLport и CRT внутри игры (`runtime`), Direct3D/DirectDraw и 2D-библиотека (`render`), окна и реестр Windows (`platform`), Bink, DirectInput, сеть | **не переносим**: это делают Python, Kivy, SDL |
| `data` | 621 | 31 тыс. | читатели .res, баз, .reg, текстов | eilib уже читает форматы, которые использует ремейк; смотрим только формат, который понадобится новой функции |
| `game` | 7577 | 360 тыс. | поведение игры | **предмет работы** |

Игровой уровень по подсистемам (missing + indirect): world 1834, ui 1297, units 859, figures 561,
player 557, magic 636, sound 432, script 373, items 317, pathing 302, ai 185, saveload 107, camera 81, math 36.

360 тысяч строк C подряд не прочитать, да и не нужно. Работу сужают три фильтра:

1. **Уровень** (сделано): backend и data отпадают — минус 2460 функций.
2. **Покрытие оригинала**: какие функции game.exe реально выполняются в сценариях demo (раздел 3). Это главный
   фильтр: всё, что оригинал не вызывает в этих сценариях, для demo не нужно.
3. **Видимая разница**: среди вызываемых функций первыми идут те, из-за которых demo выглядит или ведёт себя
   иначе, чем оригинал.

## 2. Учёт решений

Чтобы реестр показывал ход работы, у каждой разобранной функции должен остаться след:

- **Реализовано или уже было сделано без ссылки** — в комментарий или докстринг .py ставится адрес
  (`game.exe 5aea80`). Генератор сам переведёт функцию в `implemented`. Многие `indirect` и часть `missing` уже
  повторены ремейком по поведению, только адрес не указан: каждая такая находка — дешёвый плюс к покрытию.
- **Не нужно или отложено** — новый файл `re/func_decisions.json`:
  `{"5dc620": {"decision": "skip", "reason": "консоль отладки"}, "604c50": {"decision": "later", "reason": "брифинг 3D"}}`.
  `tools/func_registry.py` прочитает его и выставит статусы `skipped` и `later`. Уровень `backend` получит `skipped`
  автоматически.
- **Найденное в коде** — в новые разделы `first_scan.md` (как сейчас), имена функций — в `re/names.json`.

## 3. Покрытие оригинала: какие функции вызывает game.exe в сценариях demo

Трассировщик покрытия — маленький отладчик Win32 на C, `re/eitrace/eitrace.c`, сборка
`i686-w64-mingw32-gcc` (компилятор уже стоит). Он работает под Wine самой игры (`EvilIslands1`, Xvfb `:77`,
`eitools/eigame.sh`):

1. Запускает `game.exe` с `DEBUG_ONLY_THIS_PROCESS`. После загрузки ставит `int3` на начало каждой из ~10.5 тыс.
   игровых функций (адреса берутся из `func_registry.json`, уровни `game` и `data`).
2. На каждом срабатывании записывает адрес и время в мс, возвращает исходный байт, отступает EIP на 1 и
   продолжает. Каждая функция останавливает игру один раз, так что замедление незаметно.
3. Раз в 5 секунд заново ставит `int3` на уже сработавшие функции. Так видно, какие из них работают каждый тик:
   это ядро «жизни» зоны.
4. Сценарий управляется через `xclick.py`. Начало каждой фазы драйвер пишет в файл меток; трасса делится на фазы
   по времени. Параллельно `eigame.sh record` пишет видео для сверки с ремейком.

Результат — `build/coverage/<сценарий>.json`: `{адрес: {"first_ms", "phases", "periodic"}}`.
`func_registry.py` добавит в реестр поле `coverage`, а в FUNC_REGISTRY.md — раздел «нужно для demo».

Сценарии повторяют то, что умеет `make demo` (README, «Управление»):

| # | Сценарий оригинала | Что покрывает |
|---|---|---|
| S0 | запуск, главное меню, наведение на кнопки, окна опций и загрузки | меню, ночь и костёр меню, музыка |
| S1 | New game → сложность → ролик → zone1, окна обучения | создание мира, загрузка зоны, обучение, брифинг |
| S2 | ходьба и бег по zone1, камера, смена часа | тик мира и юнитов, путь, камера, свет, вода, туман войны |
| S3 | бой с кабаном, смерть, лут трупа | бой, ИИ, звуки, опыт, лут |
| S4 | заклинания: каст по монстру и по земле | магия, частицы, свет, иконки заклинаний |
| S5 | лагерь: предметы, информация, навыки, торговля, ремонт, конструкторы | экраны лагеря |
| S6 | быстрое сохранение и загрузка | saveload |

S4 требует героя с заклинаниями. В начале оригинальной кампании их нет, поэтому нужен сохранённый файл с

Риски. Отладочный API в Wine работает: на нём построен `winedbg`. Упаковщика у game.exe нет: Ghidra разобрала
его целиком. Если проверка диска или другая защита помешает отладчику, запасной путь — `winedbg --gdb` с
программными точками останова, пачками по 500 адресов на каждый прогон.

## 4. Очередь работ

одном сценарии. Порядок:

| Приоритет | Что | Почему |
|---|---|---|
| P1 | периодические функции S1–S3 (каждый тик зоны) | они определяют, как zone1 живёт и выглядит всё время |
| P2 | известные отличия demo от оригинала (список ниже) | пользователь видит их сразу |
| P3 | функции, вызванные один раз в S0, S1, S4–S8 | окна, переходы, загрузка, сохранение |

## 5. Как разбирается одна пачка

Единица работы — блок одного .cpp: непрерывный отрезок адресов одной подсистемы (карта отрезков — в
FUNC_REGISTRY.md, «Покрытие по блокам адресов»). Например: погода (`CWeather`, 5616c0–561b00), туман войны (`CVisibilityFog`, 4e1770–4e59f0),
ИИ 5cd500–5d7f40, интерфейс 5f74e0–5fcc00.

1. **Выгрузка.** Новый `tools/func_dump.py <от> <до>` выводит C функций блока, а над каждой — строку
   из реестра: статус, подсистема, реализованные вызывающие, покрытие трассы.
2. **Точки входа.** Виртуальные методы (`callers` = 0, у игрового уровня таких 2095) и вызовы из уже
   реализованного кода. Отсюда видно, где новая функция встанет в ремейке.
3. **Решение по каждой функции:**
   - уже сделано в Python → дописать адрес в комментарий;
   - нужно → разобрать, записать в `first_scan.md`, дать имя в `re/names.json`;
   - не нужно → `skip` с причиной.
4. **Реализация.** Поведение — в `engine`, без Kivy. Рисование — в `client`. Новый формат — в `eilib`. Тесты —
   в `tests/`. В коде — ссылки `game.exe <адрес>`, чтобы реестр их нашёл. Стиль — по CLAUDE.md.
5. **Сверка.** Тот же сценарий в оригинале (`eigame.sh record`) и в ремейке (`build/demo_drive.py`).
   Скорость проверяется на настоящем дисплее (`make demo` с `build/frame_log.py`).
6. **`make registry`** — проверить, что функции перешли в `implemented` или `skipped`, и обновить цифры
   в этом плане.
